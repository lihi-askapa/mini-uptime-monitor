# יומן למידה — שלב 1

## מה בנינו?

אפליקציית Flask שבודקת אתר לפי בקשה ושומרת את התוצאה ב-SQLite.
הסעיפים הראשונים מתארים את השלב המקומי המקורי; שלבי Docker, CI, מתזמן ופריסה בענן מתועדים בהמשך.

## הקבצים

- `app.py`: הגדרות, פנייה לאתר, שמירה במסד הנתונים ונתיבי HTTP.
- `templates/index.html`: מבנה המסך והצגת הנתונים באמצעות Jinja.
- `static/style.css`: עיצוב המסך.
- `requirements.txt`: ספריות Python הנדרשות.
- `tests/test_app.py`: בדיקות שמדמות תגובות, בלי לפנות לאתרים אמיתיים.

## מה קורה בלחיצה על Check now?

1. הדפדפן שולח POST עם מזהה של אתר שהוגדר מראש.
2. Flask בודק שהמזהה מוכר ומבצע בקשת HTTP.
3. נמדדים קוד התגובה וזמן ההמתנה לכותרות.
4. התוצאה נשמרת בקובץ SQLite עם חותמת זמן ב-UTC.
5. הדפדפן מופנה למסך שמציג את התוצאה.

## מושגים לראיון

- **HTTP status**: תגובת HTTP יכולה להגיע גם כשהתוצאה היא שגיאה, למשל 500.
- **Timeout**: אין תשובה בזמן שהוגדר; ייתכן שלא יהיה קוד HTTP כלל.
- **Health endpoint**: בודק את השירות שלנו; אתר מנוטר שנכשל אינו בהכרח תקלה במנטר עצמו.
- **Persistence**: קובץ SQLite נשאר אחרי עצירה והפעלה. בשלב Docker נצטרך Volume כדי לשמור אותו גם בהחלפת Container.
- **Logs**: כל בדיקה כותבת מזהה יעד, סטטוס, קוד וזמן לטרמינל.
- **Configuration**: משתני סביבה מאפשרים לשנות פורט, מסד ויעדים בלי לשנות קוד.

## שאלות לתרגול

1. מה ההבדל בין GET של המסך ל-POST שמבצע בדיקה?
2. למה /health יכול להיות תקין בזמן שאתר מנוטר נכשל?
3. האם תוצאה ירוקה מלפני שעה מוכיחה שהאתר זמין עכשיו?
4. מה יקרה להיסטוריה אם נמחק את קובץ מסד הנתונים?

## תיעוד אמיתי

נוסיף כאן בכל שלב מה הרצנו, איזו תקלה ראינו ואילו ראיות הובילו לפתרון.
יצירת הקוד נעשתה בסיוע AI; יש לעבור על הזרימה ולהסביר אותה לפני שמתקדמים.

## שלב 2 — הרצה ב-Docker, 25 בנובמבר 2026

נוספו Dockerfile, הגדרות Compose, Volume, משתמש אפליקציה שאינו root ושרת Gunicorn. מדריך: [מעבדת Docker](docker-lab.md).

- בניית Image ראשונה נכשלה בהורדת ספריות Python בגלל חיבור TLS לשרת הקבצים. ההתקנה הושלמה ממטמון wheels עם מקורות ואימות המתועדים במדריך.
- הקונטיינר עלה בפורט חיצוני 8081; בפנים האפליקציה מאזינה ב-8080. `/health` החזיר 200.
- בדיקת אוגדן ראשונה הסתיימה ב-timeout ונשמרה במסד. בקונטיינר חדש, עם מזהה שונה, אותה רשומה נשמרה: ה-Volume פעל.
- בדיקת example.com הצליחה ב-200. בדיקה נוספת של אוגדן הצליחה ב-200: timeout אחד אינו מוכיח נפילת אתר.
- אומת משתמש ריצה UID 10001, ונבדקו תלויות באמצעות `pip check`.
- הודעת הרשאות מתהליך הבקרה של Gunicorn חשפה שלמשתמש אין תיקיית בית. תוקנה הגדרת המשתמש כך שתיווצר תיקיית בית.

חשוב: אלה בדיקות שבוצעו בסיוע Codex. יש לתרגל את הפקודות ולהבין את התוצאות לפני שמתארים את השלב כעבודה עצמאית.

## שלב 3 — CI ומתזמן, 26 בנובמבר 2026

- המשתמשת העלתה workflow ל־GitHub ואישרה הרצה ירוקה של בדיקות Python, בניית Image ובדיקות בקונטיינר.
- תורגל כישלון מכוון: ציפייה שגויה ל־200 במקום 503 בבדיקת תקלה במסד. ההרצה נכשלה עם `AssertionError: 503 != 200`; אחרי תיקון והעלאה נוספת המשתמשת אישרה ירוק.
- נוסף שירות Compose אופציונלי בשם `scheduler`, שמופעל בפרופיל `monitoring`. הוא משתמש באותו Image ובאותו Volume של `web`, אבל מריץ פקודת `monitor` במקום Gunicorn.
- שני השירותים משתמשים באותה פונקציית `check_target`. המתזמן בודק כל יעד בתורו, שומר ב־SQLite, ממתין 60 שניות מסיום הסבב וחוזר.
- המשתמשת בנתה Image, הפעילה את הפרופיל והציגה לוגים של ארבעה סבבים מוצלחים לשלושת האתרים. כל סבב כתב התחלה, שלוש תוצאות וסיום.
- שבע בדיקות עברו מקומית, כולל שני תרחישים חדשים למתזמן. הרצת CI של שינויי המתזמן עדיין דורשת commit, push ואימות התוצאה.
- הדפדפן מתחבר רק ל־web. המתזמן כותב למסד המשותף; web קורא ממנו כשמרעננים את הדף. הופעת התוצאות החדשות במסך עדיין לא אושרה במפורש.
- ניטור מקומי תלוי במחשב וב־Docker פעילים. אפשר לעצור רק את המתזמן באמצעות `docker compose stop scheduler`.

## שלב 4 — הדגמה ציבורית ב־AWS, 26 בנובמבר 2026

- המשתמשת הקימה EC2 מסוג t3.micro באזור Stockholm עם Amazon Linux 2023 ודיסק gp3 מוצפן של 16 GiB.
- תורגלו שמירת מפתח SSH במק, אימות טביעת אצבע מול לוג המערכת וחיבור מרוחק.
- Docker ו־Compose הותקנו בשרת. קוד שנארז באמצעות git archive הועבר ב־scp, נבנה ל־Image והופעל עם Volume חדש.
- לוגי המתזמן הראו בדיקות מוצלחות לשלושת האתרים בשרת. האפליקציה נפתחה תחילה דרך מנהרת SSH.
- נוסף קאדי כקונטיינר שלישי באמצעות קובץ Compose משלים; נוצרו Volumes נפרדים לתעודות ולהגדרות שלו.
- נוספו הגנות טופס וחלון המתנה משותף לבדיקה ידנית. מספר הבדיקות עלה משבע לעשר; כולן עברו ב־CI וב־Image על EC2.
- טופלה שגיאת timeout ב־SSH: כתובת המקור הציבורית השתנתה, וכלל SSH עודכן לכתובת החדשה בלבד. לא הורחבה גישת הניהול לכל האינטרנט.
- המשתמשת אישרה שהאתר הציבורי נפתח ב־HTTPS, שהבדיקה הידנית נשמרת ושניסיון חוזר מוקדם נחסם.
- בדיקות אלה מאשרות את המסלול הציבורי הבסיסי; הן אינן בדיקת עומס או הבטחת זמינות רצופה.
- עדיין אין CD אוטומטי ואין Terraform. ההדגמה תלויה בשרת פועל, בשירות DNS חיצוני ובכתובת ה־IP הנוכחית.

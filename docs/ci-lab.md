# בדיקות אוטומטיות ב־GitHub Actions

## מה הוספנו?

קובץ `.github/workflows/ci.yml` מגדיר תהליך בדיקה אוטומטי (workflow).
GitHub קורא אותו אחרי שמעלים אותו למאגר. שמירת הקובץ במחשב בלבד אינה מפעילה אותו.

## איך קוראים את הקובץ?

- `name`: שם התהליך שיופיע בלשונית Actions.
- `on`: האירועים שמפעילים אותו. `push` הוא העלאת commits; `pull_request` הוא פתיחה או עדכון של בקשת שינוי; `workflow_dispatch` מאפשר הפעלה ידנית.
- `permissions: contents: read`: התהליך מקבל הרשאת קריאה של תוכן המאגר.
- `jobs`: העבודות שצריך לבצע. כרגע יש עבודה אחת, בשם `tests`.
- `runs-on: ubuntu-latest`: העבודה תרוץ על מכונת Linux זמנית של GitHub.
- `steps`: השלבים שיבוצעו לפי הסדר.
- `uses`: הפעלת פעולה מוכנה. כאן משתמשים בפעולה להורדת הקוד ובפעולה להכנת Python 3.12.
- `run`: פקודת טרמינל שמורצת על המכונה של GitHub.

## מה רץ ובאיזה סדר?

1. הורדת הקוד מהמאגר אל המכונה הזמנית.
2. הכנת Python 3.12.
3. התקנת הספריות באמצעות `python -m pip install -r requirements.txt`.
4. הרצת `python -m unittest discover -s tests -v`.

זו אותה פקודת בדיקות שלמדנו. לא מוסיפים לפניה `docker compose exec web`,
כי כאן מריצים אותה ישירות במכונת GitHub, ולא בקונטיינר שבמחשב שלנו.

בדיקה שנכשלת מחזירה קוד יציאה שאינו אפס וגורמת לעבודה להיכשל.
אפשר לפתוח את ההרצה בלשונית Actions ולראות בדיוק באיזה שלב ומה הודעת השגיאה.
כישלון לא עוצר את האפליקציה במחשב ולא חוסם מיזוג אוטומטית; חסימת מיזוג דורשת הגדרת כללי ענף בנפרד.

## גבולות השלב

הבדיקות מדמות תגובות HTTP ומשתמשות ב־SQLite זמני.
הן אינן פונות לאתרים אמיתיים ואינן נוגעות בהיסטוריה שב־Volume שלנו.
כאן עדיין לא בונים Image ולא פורסים לענן. זה שלב CI, לפני פריסה אוטומטית.

## התקלה שלמדנו ממנה ב־Docker

בתחילה הרצנו בדיקות בתוך קונטיינר שלא הכיל את תיקיית `tests`.
הוספנו הוראת COPY ב־Dockerfile והסרנו את התיקייה מ־`.dockerignore`.
לאחר בניית Image והחלפת הקונטיינר, המשתמשת הריצה את חמש הבדיקות וכולן עברו.
הודעת Database health check failed צפויה בבדיקה שמדמה תקלה במסד, כאשר הבדיקה עצמה מסתיימת ב־ok.
